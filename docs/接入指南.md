# TrellisForge 嵌入式 C 接入指南

## 目的和边界

本指南将 TrellisForge 的项目级覆盖层接入一个已经是 Git 仓库的嵌入式 C
项目，并把“首次接入 1.3”“从 1.0、1.1 或 1.2 升级到 1.3”“升级上游 Trellis”
三种流程分开描述。

TrellisForge 不是 Trellis 的私有分叉：先运行 `trellis init`，再叠加项目级
文件。不要从范例复制 `.trellis/tasks/`、`.trellis/workspace/`、
`.trellis/.runtime/` 或 `.trellis/.template-hashes.json`；这些都是目标仓库
自己的运行状态。

当前覆盖层默认交付三个平台：Claude Code、Codex 与 OpenCode。OpenCode 使用
原生 Task 子代理与 `.opencode/plugins/` 上下文注入，需要 Node.js 运行时；
`trellis channel` 的 worker provider 仍只支持 `claude|codex`，OpenCode 的
`trellis mem` 读取器不在本次支持范围，真实 OpenCode CLI/TUI 端到端也尚未在
当前环境验证。不要据此为其他平台创建代理、Hook 或派发分支。

## 目录说明

```text
templates/embedded-c-overlay/
  AGENTS.md.template                         项目规则与 Trellis 入口模板
  TEMPLATE-CONTENTS.md                       覆盖层内容清单（Forge 维护者阅读）
  .trellis/                                  工作流、门禁脚本、channel 代理、Spec 骨架
  .agents/skills/                            Grill Me、审查、收尾与完整 trellis-channel Skill
  .claude/                                   Claude Code 代理、Hook、设置
  .codex/                                    Codex 代理、Hook、设置
  .opencode/                                 OpenCode 插件、代理、命令与 Skill 完整闭包（1.3 起不含 package.json；仅交付 .gitignore）
tools/install-embedded-c-overlay.ps1         首次接入安装器（1.3）
tools/update-embedded-c-overlay.ps1          电梯模型升级器（默认预检、-Apply 应用）
tools/lib/TrellisForgeOverlay.psm1           安装器与升级器共享模块
history/embedded-c-overlay/                  canonical 对象库 + 1.0/1.1/1.2/1.3 版本 manifest
migrations/embedded-c-overlay/structural/    相邻结构迁移步骤（1.0-to-1.1、1.1-to-1.2、1.2-to-1.3）
tests/test_overlay_tools.py                  安装/升级临时 Git 仓库自动化测试
```

`__PROJECT_PREFIX__` 是目录名占位符，例如 `motor`；`PROJECT_PREFIX` 和
`PROJECT_NAME` 是文件正文中的占位符。安装器和升级器会统一替换三者。

# 一、首次接入 TrellisForge 1.3

1. 进入目标仓库根目录，阅读已有 `AGENTS.md`，并记录 `git status --short`。
   不覆盖用户已有变更。
2. 在目标根目录运行 `trellis init`。它提供与当前 Trellis 版本（本模板针对
   `0.6.10`）匹配的基础 runtime、内置 Skills 和默认文件。
3. 在 TrellisForge 根目录运行：

   ```powershell
   & .\tools\install-embedded-c-overlay.ps1 `
     -TargetRoot C:\work\example-firmware `
     -ProjectPrefix example `
     -ProjectName "Example Firmware" `
     -Force
   ```

   首次接入必须使用 `-Force`：`trellis init` 会创建 Forge 必须替换的
   `.trellis/workflow.md`、`.trellis/config.yaml` 和脚本。脚本会先把所有
   将被模板覆盖的既有文件备份到 Git 元数据目录下的
   `.git/trellisforge-backup/<时间戳>-<GUID>/`，并写出含原文件 SHA-256 的
   `backup-manifest.json`，再完整覆盖为模板版本。`-Force` 不会自动合并任何
   自定义文件；它只保证原文件可恢复。请在运行 `-Force` 前完成必须保留的
   平台文件迁移。备份默认不属于工作树，不会出现在 `git status` 中；需要长期
   留档时，请主动复制到仓库外的安全位置。

   对已有 Trellis 定制的仓库，先不带 `-Force` 运行一次以列出冲突，再审查
   目标文件与备份范围后才运行上面的命令。脚本只覆盖模板清单中的项目级
   定制文件，不删除目标仓库文件。

4. 首次安装成功后，目标仓库多了一个 `.trellis/trellisforge.json` 安装收据，
   内容包含 schema 版本、TrellisForge 版本（`1.3`）、覆盖层类型
   （`embedded-c`）、项目名称/前缀和受管文件摘要；每个文件记录三类哈希：
   `canonical_sha256`（渲染前 canonical 对象哈希，可定位到
   `history/embedded-c-overlay/objects/<sha256>`）、`baseline_sha256`（按项目
   参数渲染后的基线）和 `installed_sha256`（实际安装结果）。该收据是后续
   升级的来源识别依据，可以提交进仓库。1.3 不安装
   `.opencode/package.json`，该依赖清单由本机生成（见第 7 步）。
5. 将 `templates/embedded-c-overlay/AGENTS.md.template` 的知识合并到目标根
   目录 `AGENTS.md`。这是合并，不是覆盖：保留原有项目规则，将模板中的
   `<...>` 全部替换为可验证的本项目事实。合并后必须确认：

   - 原 `AGENTS.md` 的项目约束仍在，除非与用户明确要求冲突；
   - 恰好存在一对 `<!-- TRELLIS:START -->` / `<!-- TRELLIS:END -->` 管理块；
   - 该块保留 `.trellis/`、`.agents/skills/`、`.claude/agents/`、
     `.codex/agents/`、`.opencode/agents/` 的位置和 Trellis 工作流入口；
   - 块外写入真实仓库结构、构建命令、测试/静态检查、硬件验证边界和受保护
     合同；
   - 不遗留 `<...>` 占位符；
   - 不删除 `session_auto_commit: false`、规划收敛/后续用户批准和项目级
     Skill 路由等 TrellisForge 规则。
6. 填写 `.trellis/spec/shared/`：至少完成仓库结构、构建命令、静态检查、
   硬件验证边界和不可修改的硬件合同。按模块增加包级 Spec，并在
   `.trellis/config.yaml` 配置实际 packages。
7. 平台接入确认：

   - 对 Claude Code：确认模板的 `.claude/settings.json`、代理、Hook 和命令
     已成为目标配置，并确认 `plan-pretool-reminder.py` 已在 settings 注册。
     该提醒负责显示执行计划状态和编辑次数警告，属于非阻断的辅助层。
   - 对 Codex：确认模板的 `.codex/hooks.json`、`.codex/config.toml`、代理和
     Hook 已成为目标配置，仓库已信任、用户级 `[features].hooks = true`，并在
     `/hooks` 中批准项目 Hook。Codex 没有 Claude 的 `PreToolUse` 等价 Hook；
     接入执行计划时必须依赖 `plan.py` CLI、UserPromptSubmit/SubagentStart
     上下文和独立质量检查。
   - 对 OpenCode：安装 Node.js 与 `trellis` CLI 后，进入目标 `.opencode/`
     目录手工创建本机依赖声明（例如 `package.json` 写入
     `"dependencies": { "@opencode-ai/plugin": "<当前版本>" }`），再运行
     `npm install @opencode-ai/plugin`。覆盖层不再官方交付
      `.opencode/package.json`，而是安装 `.opencode/.gitignore` 忽略本机的
      `package.json` 与 `package-lock.json`，让依赖产物从一开始不进 git。
      `.gitignore` 只对未跟踪文件生效：已经进过 Git 的 `package.json` 仍会
      显示为已修改，必须先取消跟踪（见升级后提交一节），ignore 才会挡住后续
      本机改动。OpenCode 主工作流使用
     `.opencode/agents/` 的原生 Task 子代理，由 `.opencode/plugins/` 注入会话
     启动、逐轮 workflow-state 与子代理上下文。限制：channel worker provider
     仍仅 `claude|codex`；OpenCode 下 `trellis mem` 读取器不可用；真实
     OpenCode CLI/TUI 端到端未在当前环境验证，首次用于产品代码前请先执行
     下面的接入冒烟。
8. 接入执行计划门禁（首次进入 Phase 2 前完成）：

   执行计划属于每个任务目录，不复制范例任务的运行状态。确认任务已经完成
   Phase 1 的规划收敛和后续用户批准，并由 `task.py start` 进入
   `in_progress`；然后在目标仓库根目录按下面的循环操作。`<task-path>` 必须
   是包含 `task.json` 的实际目录，例如 `.trellis/tasks/09-01-add-feature`，
   不要写 `.trellis/tasks` 容器目录。

   - 正常情况下，`trellis-implement` 会先读取 `prd.md`、`design.md`（如有）、
     `implement.md`、相关 Spec 和代码，再自行生成并校验 `execution-plan.json`。
     以下手工命令仅用于首次接入冒烟、inline/无代理执行或 Hook/代理不可用时
     的兜底；只有任务确实没有计划文件时才执行：

     ```powershell
     $taskPath = "<task-path>"
     $template = (& python .trellis/scripts/plan.py --task $taskPath template | Out-String)
     [System.IO.File]::WriteAllText(
       (Join-Path $taskPath "execution-plan.json"),
       $template,
       [System.Text.UTF8Encoding]::new($false)
     )
     ```

     上面的命令会以 UTF-8 无 BOM 写入任务目录内的 `execution-plan.json`；然后
     补全目标、最多 8 个阶段、`depends_on`、`scope.read`/`scope.write` 以及
     `verification` 的 `level`/`required_checks`。正常任务应以末端 `report`
     阶段收尾，使用 `report_path: "final-report.md"` 并传递依赖所有其他阶段；
     若确有任务不设置 report 阶段，需在 2.2 独立质量检查中明确补充最终验收
     和报告缺口。不要在计划获批前修改业务源码。

   - 运行 `python .trellis/scripts/plan.py --task "<task-path>" validate`。
     校验成功会将计划置为 `approved`；工作流要求只有此状态才进入源码编辑。
     `plan.py` 不会拦截绕过流程的任意文件编辑，因此仍须遵守项目代理和独立
     审查约束。随后用 `status` 查看当前阶段和下一可运行阶段。

   - 每个编辑阶段都按以下顺序推进。产品源码和配置只修改该阶段声明的
     `scope.write`；任务目录内的 `final-report.md` 等审计产物是允许的输出，
     不应误写成产品源码范围：

     ```powershell
     python .trellis/scripts/plan.py --task "<task-path>" start <phase-id>
     # 执行实际编辑和项目定义的检查/构建
     python .trellis/scripts/plan.py --task "<task-path>" record <phase-id> `
       --check <check-id> --result pass --command <命令标识> --exit-code 0 `
       --summary "<简短结果>" [--artifact <任务内相对路径>]
     python .trellis/scripts/plan.py --task "<task-path>" done <phase-id>
     ```

     `record` 只是记录已经执行的结果，`plan.py` 不会运行构建、测试或硬件
     验证。`minimal` 阶段必须为每个 `required_checks` 记录结果；只有纯只读
     阶段才能用非空 `no_check_reason` 省略检查。若设置 `report` 阶段，则必须
     写入并通过 `--artifact final-report.md` 登记最终报告；阶段完成前所有
     声明的检查都必须通过。不可执行的声明检查不能记录为通过，应通过
     `block`/`revise` 处理，并在最终报告或最终消息中说明。阶段之间运行
     `status`，全部完成后才进入 2.2 独立质量检查。

   - 计划不正确或检查失败时，先记录原因，再修订计划：

     ```powershell
     python .trellis/scripts/plan.py --task "<task-path>" block <phase-id> --reason "<原因>"
     python .trellis/scripts/plan.py --task "<task-path>" revise --reason "<修订原因>"
     # 编辑 execution-plan.json 后重新校验
     python .trellis/scripts/plan.py --task "<task-path>" validate
     ```

     如果 CLI 报告 `execution-events.jsonl` 损坏，必须先修复无法解析的日志行，
     在日志恢复前不得手工改状态或继续任何状态变更。Hook 提供的
     `<execution-plan>` 面包屑和子代理提示只是显示/提醒层；即使 Hook 被禁用，
     上述 CLI 流程也必须可用。

9. 运行验证：

   ```powershell
   python -B -m unittest discover -s .trellis/scripts/tests -p "test_*.py"
   $hookFiles = @(
     Get-ChildItem .claude/hooks,.codex/hooks -Filter *.py -File |
       ForEach-Object { $_.FullName }
   )
   python -m py_compile $hookFiles
   git diff --check
   ```

   在 Claude Code 中再确认 `/trellis:continue` 与 `/trellis:finish-work` 均能
   加载；在 OpenCode 中确认对应的 `.opencode/commands/trellis/` 命令与
   `.opencode/agents/` 子代理定义已就位；它们只能路由到项目的 workflow 与
   Skill，不能绕过代码提交、归档和 bookkeeping 的用户批准边界。

10. 创建一个仅文档的小任务，确认规划收敛、用户后续批准、`task.py start`、
    执行计划的 `template`/`validate`/`start`/`record`/`done` 循环、
    implement/check 派发（含派发后首次工作前的上下文预检）、Hook 注入和
    `trellis-finish-work` 收尾边界均按预期工作后再用于产品代码。

# 二、从 TrellisForge 1.0、1.1 或 1.2 升级到 1.3

`tools/update-embedded-c-overlay.ps1` 是电梯模型升级器，目标永远是 `VERSION`
指向的当前版本（现为 1.3）。它不保存逐对 `new/` 快照：历史版本正文从 Forge 侧
canonical 内容库（`history/embedded-c-overlay/objects/`）与版本 manifest
（`versions/1.0`、`versions/1.1`、`versions/1.2`、`versions/1.3`）取得。升级器
比较来源/目标完整 manifest，对 canonical 对象相同的受管路径保持工作树不变，对
对象变化的路径执行“canonical old + 当前文件 + 1.3 模板”三方文本合并，对
adoption-baseline 路径执行接管合并，对 1.3 新增文件按缺失/一致/冲突分类。文件
正文一律从来源版本一步直达 1.3：1.0 与 1.1 来源都不会读取或落盘中间版本正文；
只有结构迁移按相邻步骤组合（1.0 来源依次加载 `1.0-to-1.1`、`1.1-to-1.2` 与
`1.2-to-1.3`，1.1 来源加载后两者，1.2 来源只加载 `1.2-to-1.3`）。它不做全量
覆盖，也不删除目标仓库文件；来源独有路径由聚合结构步骤的 `remove` 动作接管，
只退出 1.3 受管集合与新收据（例如 1.2 的 `.opencode/package.json`），磁盘文件
保持不动。

三类来源的识别方式：

- **1.1 或 1.2 项目（有 `.trellis/trellisforge.json` 收据）**：来源版本与
  `ProjectPrefix`/`ProjectName` 自动从收据读取；收据与传入参数不一致时
  fail closed。
- **1.0 项目（没有安装收据）**：必须显式提供原安装使用的项目参数；省略
  `-FromVersion` 时默认按 1.0 入场候选预检。

## 升级前准备

1. 确认目标仓库是 Git 仓库且已运行 `trellis init`。
2. 在 TrellisForge 根目录运行 `trellis update --dry-run`，记录上游 Trellis
   状态；如果上游要求，先处理上游更新，再回到本升级（升级器不会整体
   `trellis update --force`，也不会修改 `.trellis/.version` 与
   `.trellis/.template-hashes.json`）。
3. 保存当前 `git status` / `git diff`；升级器只处理受管模板文件，但建议先
   提交或保存你的工作区改动。

## 预检（默认模式，不写入）

```powershell
# 1.1 或 1.2 收据项目
& .\tools\update-embedded-c-overlay.ps1 -TargetRoot C:\work\example-firmware

# 1.0 无收据项目（参数必填，也可显式 -FromVersion 1.0）
& .\tools\update-embedded-c-overlay.ps1 `
  -TargetRoot C:\work\example-firmware `
  -ProjectPrefix example `
  -ProjectName "Example Firmware"
```

1.0 入场预检会依次验证 1.0 manifest、canonical 对象、相邻结构链与三方合并
兼容性；默认来源版本只是入场候选，无法确认兼容即以 `unsupported` 停止，
工具不猜测项目参数。其他无收据来源版本（如 `0.9`）会被判定为
`unsupported` 并停止。

预检结果为每条受影响路径给出 `add`、`update`、`already-current`、
`user-merged`、`structural-remove`、`conflict` 或 `unsupported`：

- `add`：1.3 新增文件，目标缺失，将直接新增；
- `update`：无用户差异，按 1.3 模板更新；
- `user-merged`：在 1.3 基础上保留了非重叠用户定制（基于“渲染后的来源
  基线 + 目标当前文件 + 渲染后的 1.3 模板”的三方文本合并）；
- `already-current`：当前内容已满足，无需修改；
- `structural-remove`：来源独有路径已由结构迁移链显式接管（如 1.2 -> 1.3 的
  `.opencode/package.json`），应用后退出 1.3 受管集合与新收据，但工具不写入、
  不删除该磁盘文件；
- `conflict` 或 `unsupported`：整次升级 fail closed，工作树零写入。

## 冲突处理

任一 `conflict` 或 `unsupported` 都会阻止整次工作树写入和 1.3 收据更新。
诊断材料写在与目标 Git 同库的元数据目录：

```text
.git/trellisforge-upgrade/<时间戳>-<GUID>/
  report.json
  report.txt
  candidates/<目标相对路径>
```

`report.txt` 可读地列出冲突路径、动作和建议下一步；`candidates/` 下保存带
old/current/new 标签的三方冲突结果（或新增文件冲突时的 1.3 候选内容）。请
根据这些材料手工解决目标仓库中的文件，然后重新运行升级器预检；只有全部路径
无冲突时才允许应用。

升级器不提供忽略冲突或部分应用的参数。

## 应用升级

预检全部通过（无冲突、无 unsupported）后显式加 `-Apply`：

```powershell
# 1.1 或 1.2 收据项目
& .\tools\update-embedded-c-overlay.ps1 `
  -TargetRoot C:\work\example-firmware `
  -Apply

# 1.0 无收据项目
& .\tools\update-embedded-c-overlay.ps1 `
  -TargetRoot C:\work\example-firmware `
  -FromVersion 1.0 `
  -ProjectPrefix example `
  -ProjectName "Example Firmware" `
  -Apply
```

应用事务顺序：

1. 把每个将被修改的既有文件（以及旧收据，如有）及 SHA-256 备份到
   `.git/trellisforge-backup/<时间戳>-<GUID>/`，同时写 `backup-manifest.json`
   （记录来源版本、目标版本、计划动作和新增路径）；
2. 原子写入所有路径结果（保留目标文件原有 LF/CRLF 换行风格），新增缺失文件
   （含 `.opencode/.gitignore`）；`structural-remove` 路径不写入、不删除；
3. 重算三类哈希并写 `.trellis/trellisforge.json` 1.3 收据（最后一个步骤）：每个
   受管文件记录渲染前 `canonical_sha256`（canonical 对象哈希）、渲染后
   `baseline_sha256`（按项目参数渲染的 canonical）与实际结果的
   `installed_sha256`；后续升级的 old 永远从 canonical 对象取得，不使用含用户
   定制的 installed 结果作为祖先；已退出的来源独有路径不进入新收据；
4. 任何一步失败都会恢复原文件与旧收据、删除本次新增文件，并以非零退出码
   结束，不会留下部分 1.3 状态。

应用完成后提交前先审查：

```powershell
git status --short
git diff
```

确认 `.trellis/workflow.md`、`.trellis/agents/` 为 1.3 形态（含五级审查路由与
上下文预检合同）、`.opencode/.gitignore` 已就位、三套 channel Skill 引用树
一致后提交。若来源为 1.2 且仓库曾跟踪 `.opencode/package.json`，升级器只会让
它退出 1.3 收据，不会删除磁盘文件。此时 `.gitignore` 已经列出 `package.json`，
但 Git 对已跟踪路径会忽略该规则，所以 `git status` 仍可能显示 `M`。正确步骤：

```powershell
git rm --cached .opencode/package.json
git status --short
```

`--cached` 只从索引拿掉该文件，磁盘上的本机依赖声明保留。随后它应变为被忽略
的未跟踪文件，不再出现在工作区脏列表。不要使用不带 `--cached` 的 `git rm`，
那会删掉工作树里的 `package.json`。确认忽略生效后再把这次索引变更与升级结果
一起提交。

## 升级后验证与幂等

- 再次运行预检命令，应报告 `already-current` 并安全退出（不重复修改、不
  生成额外冲突）。1.0、1.1 和 1.2 来源升级完成后行为相同。
- 运行目标仓库的脚本与 Hook 验证命令（与首次接入第 9 步相同），再创建一个
  仅文档的小任务做接入冒烟。
- 确认 `.opencode/.gitignore` 已生效：本机生成的 `package.json` 与
  `package-lock.json` 不再出现在 `git status`。若仍显示已修改，说明该路径
  还在 Git 索引里，ignore 不会生效；按上一节执行 `git rm --cached` 后再查。
- 升级会保留 `.trellis/.version` 与 `.trellis/.template-hashes.json` 中的
  上游状态，不会伪造或整体覆盖它们。

# 三、升级上游 Trellis

接入后必须把 `.trellis/spec/shared/trellis-maintenance.md` 视为维护合同。
升级 Trellis 时先执行 `trellis update --dry-run`，版本变化使用 `--create-new`
并逐项迁移，不使用整体 `--force` 覆盖项目定制。

单独升级上游 Trellis 的步骤：

```powershell
# 记录当前差异
git status --short
git diff > %TEMP%\trellis-before.diff
# 查看上游将修改的文件（不会写入）
trellis update --dry-run
# 版本变化时用 --create-new 取得上游新文件，再逐项比较合并
trellis update --create-new
```

升级后重新应用 TrellisForge 覆盖层并逐项审查冲突，再按
`trellis-maintenance.md` 重跑门禁单测、Hook/代理解析和小型冒烟任务。
TrellisForge 升级与上游 Trellis 升级是两条独立通道：上游升级不改变 Forge
版本事实，Forge 升级也不会强行执行 `trellis update --force`。

## 嵌入式 C 特化项

该范例假定代码可能受中断、DMA、Flash、寄存器、启动文件、链接脚本和板级
验证约束。模板因此要求：

- 项目规则明确受保护的引脚、DMA、时钟、Flash、协议、调度周期和构建输入；
- 构建与静态检查使用项目真实命令，不虚构 Web 的 lint/typecheck；
- Claude implement/check 和 finish prompt 已直接替换为项目定义验证合同，
  接入 AI 不得改回泛化 `lint/typecheck`；
- 构建、静态检查、单元测试和实体硬件验证分开报告；
- 变更 ISR、共享状态、持久化、协议或硬件合同必须扩大到直接调用者和相关
  Spec；
- 新函数的注释说明单位、范围、阻塞性、中断上下文、可重入性及硬件副作用。

这些规则写在 `AGENTS.md.template`、项目级代理定义和
`spec/shared/*.md` 中。接入时必须把占位符改成真实工具链、目标板和约束；
不能把范例当作对所有 MCU 都正确的硬件事实。

## 换用其他语言时改哪里

工作流的规划门禁、任务上下文注入、批量探索、分阶段验证、停止条件和审查
profile 是语言无关的，可以保留。必须替换以下 C 特化内容：

1. `AGENTS.md`：删除 MCU/ISR/DMA/Flash/寄存器约束，写入该语言的并发、
   依赖、迁移、兼容性和发布约束。
2. `.agents/skills/__PROJECT_PREFIX__-trellis-review/SKILL.md`：替换嵌入式
   风险检查与验证报告字段。
3. `.trellis/agents/implement.md` 和 `check.md`：将“嵌入式 C 检查、目标构建、
   硬件验证”换成项目实际检查，并同步报告格式。
4. `.trellis/workflow.md`：替换语言/领域相关的检查、Spec 和术语，保留
   Grill Me、规划收敛门禁、派发边界、批量操作、阶段验证和停止条件。具体
   替换见 `templates/language-adaptation/non-embedded-c-workflow-replacements.md`。
5. `.claude/agents/trellis-*`、`.codex/agents/trellis-*`、
   `.opencode/agents/trellis-*`、两个 `inject-subagent-context.py` 和
   `.opencode/lib/`、`.opencode/plugins/` 中的 JS 定制：把“不要发明 Web
   命令”的 C 特化表述改为实际语言命令策略。
6. `.trellis/spec/shared/`：用语言和架构对应的代码规范、测试策略、部署/迁移
   合同替换嵌入式模板。

不要仅替换构建命令而保留 ISR、DMA、硬件验证等术语，否则审查代理会得到错误
的任务模型。
